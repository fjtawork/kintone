# 更新配布戦略メモ（売り切りモデル）

最終更新: 2026-02-17

## 1. 前提

- 本プロダクトは基本的に売り切り（バージョンごと販売）を想定。
- 顧客ごとに専用環境（主に VPS / Docker Compose）で運用する想定。
- 顧客がしばらく未利用・未更新になるケースを許容する。
- 強制アップデートは必須にしない。

## 2. 運用方針（合意事項）

- 更新は「強制自動更新」ではなく「管理者主導の手動更新」を基本とする。
- 管理画面で更新通知を表示し、必要に応じて顧客管理者メールにも通知する。
- 顧客は提示された手順・ファイルで自分で更新を実行できるようにする。

## 3. 将来実装する仕組み（優先順）

### 3.1 バージョン可視化

- `GET /api/v1/system/version` を追加し、以下を返す。
  - `app_version`
  - `git_sha`
  - `build_time`
  - `schema_revision`（Alembic）
- 管理画面フッター/管理ページにも表示する。

### 3.2 更新通知（管理画面）

- 管理者向け通知センターに「新バージョンあり」を表示。
- 表示項目:
  - 対象バージョン
  - 重要度（critical/high/normal）
  - 変更概要
  - 手順リンク
  - リリースノートリンク

### 3.3 配布単位（Release Bundle）

- 版ごとに配布物を固定化:
  - `upgrade.sh`
  - `rollback.sh`
  - `release_notes.md`
  - `checksums.txt`
- 管理画面からダウンロードできるようにする（将来的に）。

### 3.4 更新安全装置

- 更新前バックアップ必須（DB dump）。
- 更新後ヘルスチェック実行。
- 失敗時はロールバック手順を画面に表示。

### 3.5 互換性ルール

- SemVer（major/minor/patch）運用。
- DBマイグレーション前提の更新手順を標準化。
- セキュリティ/バグ修正は patch リリース中心。

## 4. 今回の実装コンテクスト（2026-02-17 時点）

### 4.1 既に実装済み（関連機能）

- レコードチャット機能（1レコード単位）
  - チャット ON/OFF、保持件数設定（アプリ設定）
  - 保持件数超過時の古いコメント自動削除
- `@` メンション候補表示（権限フィルタ済み）
- メンション時の画面通知（ベル通知）
  - 通知内容: アプリ名、送信者、メッセージ先頭20文字
  - 通知リンクから対象レコードへ遷移
- チャット UI 改善
  - 自分/他人の吹き分け
  - URL自動リンク化
  - メンション表示ハイライト
  - 入力欄の自動高さ調整

### 4.2 テストDB運用の前提

- 開発DBとテストDBを分離 (`TEST_DATABASE_URL`)。
- テスト時は本番/開発DBを使わないガードを導入済み。

## 5. 将来チケット化のための実装候補

- `system/version` API + 管理画面表示
- `health/live` と `health/ready`
- 更新通知データ構造（例: `update_notices`）
- 管理画面「更新ウィザード」
  - 現在版確認
  - バックアップ確認
  - 更新コマンド提示
  - 反映後チェック
- 配布物テンプレート（upgrade/rollback scripts）

## 6. 補足

- 売り切りモデルでは「顧客が更新しない自由」を許容しつつ、重大脆弱性時の告知経路を確保することが重要。
- 自動更新よりも「可視化・手順標準化・復旧可能性」の設計を優先する。
